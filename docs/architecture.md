# Officina architecture

Officina is a collaborative software workshop. People describe what they need, agents turn it into specs, code and reviews, and people decide at every point that matters. Developers and non-developers work on the same board, on the same tasks, with the same audit trail.

This document is the source of truth for how Officina works. Anything that contradicts it is a bug in either the code or this page.

## 1. Principles

1. **Collaborative first.** Every surface is multi-user: shared board, task threads, mentions, approvals by policy, notifications, presence. A single-user flow is a special case of a team flow, never the other way round.
2. **Review is the bottleneck, not typing.** Officina optimizes human minutes per merged change. Agent throughput only matters when people can keep up with it.
3. **People decide, agents do.** What gets built (the spec) is always a human decision, and so is checking the result, except for low-risk changes a project explicitly lets through (section 8). Merging is a person's act unless a project allows auto-merge and the chooser decides a given result can land on its own (section 8); agents never approve their own work.
4. **The engine is deterministic.** State transitions, scheduling, claims, retries, limits and stuck-work detection are plain code. Models run only inside stage agents, and their output is a typed contract the engine validates.
5. **Risk is mechanical.** Which lane a change belongs to is decided by path rules on the actual diff, not by a model's opinion. Lanes decide which approvals are needed.
6. **Humans and agents are interchangeable workers.** Any build or review step can be assigned to an agent or claimed by a person, and handed back and forth.
7. **Code lives in GitHub.** Officina never replaces the repository, its CI or its branch rules. It opens branches and PRs through its GitHub App and mirrors progress back to issues.
8. **Everything is attributed.** Every event records a human member or an agent role at a specific version.
9. **Consumer-agnostic.** Nothing project-specific lives in Officina. A project brings a config file and its own docs.
10. **Agent-legible.** Officina's own docs are written for agents as first-class readers, and Officina is built with Officina as soon as it can be.

## 2. People and roles

Roles are per project and live in Officina, never in repository permissions. A member only needs a GitHub account to merge. Each member of a project has one role there and any number of **approval domains** (for example `product`, `design`, `legal`, `finance`): a role says what they may do, a domain says which approvals they can give.

**The permission matrix.** What each role may do is written once, in `PERMISSIONS` (`packages/core/src/permissions.ts`), as the least role that may take each action; roles are ordered, so each role may do everything the one below it may. The lifecycle (`decide`), the board's views and actions, the API, the CLI and the Claude connector all ask `can(member, action)`, and the board receives each member's actions from the API (`can` on every project of `/api/me`) instead of comparing roles itself. A test keeps this table equal to the code.

| Action             | What it lets a member do                                                                                          | Watcher | Contributor | Maintainer | Owner |
| ------------------ | ----------------------------------------------------------------------------------------------------------------- | ------- | ----------- | ---------- | ----- |
| `see`              | see every task in the project, its thread and every decision                                                      | yes     | yes         | yes        | yes   |
| `request`          | open requests                                                                                                     | no      | yes         | yes        | yes   |
| `comment`          | comment                                                                                                           | no      | yes         | yes        | yes   |
| `answer`           | answer the questions asked of them                                                                                | no      | yes         | yes        | yes   |
| `approve_spec`     | approve a plan when its approval policy names them                                                                | no      | yes         | yes        | yes   |
| `verify_result`    | check a result when its approval policy names them                                                                | no      | yes         | yes        | yes   |
| `triage`           | accept or decline requests, and send anyone's request on                                                          | no      | no          | yes        | yes   |
| `build`            | claim a build and hand it in, built by hand or with their own agents (also anyone with the `developer` domain)    | no      | no          | yes        | yes   |
| `steer`            | pause, resume, review by hand or cancel any task, and hand a claimed build back                                   | no      | no          | yes        | yes   |
| `see_runs`         | see agent runs, their logs and costs                                                                              | no      | no          | yes        | yes   |
| `decide_learnings` | accept or reject learnings                                                                                        | no      | no          | yes        | yes   |
| `merge`            | merge results on GitHub                                                                                           | no      | no          | yes        | yes   |
| `see_confidential` | read and approve tasks that touch the project's confidential content (also anyone with the `confidential` domain) | no      | no          | yes        | yes   |
| `publish`          | approve anything that publishes, deploys, changes access or touches secrets                                       | no      | no          | no         | yes   |
| `manage_members`   | invite members and change their roles                                                                             | no      | no          | no         | yes   |
| `see_access_log`   | see who signed in, who sent sign-in links and which apps each member connected                                    | no      | no          | no         | yes   |

A domain can grant one action below its least role (`DOMAIN_GRANTS`): the `confidential` domain lets a contributor, for example a CEO, read and approve confidential tasks without becoming a maintainer. Three rules sit on top of the matrix. Approving a plan or checking a result, or sending either back for changes, also needs the gate's approval policy to name the member, by role, by domain or as the requester (section 3). A question is answered by whoever it is asked of (a member or a role), and an owner may answer any. The requester may always cancel their own request.

**Everyone sees the work.** Every member of a project, watchers included, sees every task in it, whoever asked for it: the board lists them all, the realtime stream sends every change in the member's projects, and the connector's `list_tasks` lists every task in progress. What differs by role is detail, not tasks: agent runs, logs, costs and learnings are for `see_runs` (section 9).

**The people of a task.** A task names, separately, the **requester** (who asked), the **approvers** of each gate (who the policy expects to approve the plan and to check the result, for example a product approver and a maintainer for the technical side), the members the chooser **asked to check** (a request, not a requirement), and **who merges** (a member with `merge` on GitHub, or GitHub itself when auto-merge applies). The requester is never assumed to be the final approver: they approve only where a requirement names them (`{ requester: true }`), or where they hold the role or domain a requirement asks for. A project that wants someone other than the requester to approve every gate sets `approvals.self_approval: false` (section 11): the requester's approval then meets only the requester requirement, and every role, domain and the maintainer floor needs someone else, unless nobody else in the project can meet it, so a small team is never stuck. The task page and the connector's `show_task` show all of them, with who already approved.

**At a glance.** The matrix above is the rule; this is the same thing by person, with the approver and builder roles most projects name. "Named" means the gate's policy asks for them: by role, by domain, or as the requester.

| Who                | How a project sets it                              | Sees every task | Requests, comments, answers | Approves the plan | Checks the result | Triage | Claims a build and hands it in | Pauses or cancels any task | Sees runs and costs | Merges | Manages members |
| ------------------ | -------------------------------------------------- | --------------- | --------------------------- | ----------------- | ----------------- | ------ | ------------------------------ | -------------------------- | ------------------- | ------ | --------------- |
| Watcher            | role `watcher`                                     | yes             | no                          | no                | no                | no     | no                             | no                         | no                  | no     | no              |
| Contributor        | role `contributor`                                 | yes             | yes                         | when named        | when named        | no     | no                             | no                         | no                  | no     | no              |
| Product approver   | any contributor or above with the `product` domain | yes             | yes                         | when named        | when named        | no     | no                             | no                         | no                  | no     | no              |
| Developer          | any contributor with the `developer` domain        | yes             | yes                         | when named        | when named        | no     | yes                            | no                         | no                  | no     | no              |
| Technical reviewer | role `maintainer` (the floor every gate needs)     | yes             | yes                         | yes               | yes               | yes    | yes                            | yes                        | yes                 | yes    | no              |

Who does what in one task's life, where the requester, the approvers and the person who merges can all be different people:

```
request      the requester (anyone with `request`) asks; the interviewer may ask them questions
triage       a maintainer accepts or declines
spec_review  the plan's approvers: the lane policy, plus what the chooser added, plus one maintainer or owner;
             the requester counts only where a requirement names them or self_approval allows it
building     the builder agent, or a developer who claims the build and hands it in, built by hand
             or with their own agents; either way it goes to the same review
verifying    the result's checkers, by the same rule with the lane's `verifying` policy
merging      a person with `merge` on GitHub, or GitHub itself when auto-merge applies
```

**Identity.** Today a member signs in with a one-time link: an owner mints it with `login-link`, or `invite` adds a person with a role and returns their first link. A member's first sign-in is recorded on them (`members.first_signed_in_at`) in the same transaction that spends the link, and it puts a notification in the Inbox of every owner of each of their projects (`invite_accepted`); only the first sign-in finds the column empty, so it goes out once. Owners and maintainers see who accepted and who is active with `members` or on the board's Members page. An owner can make a fresh invite link there, but only for a member who has never signed in, and only when they may manage that member in every project the member belongs to (`managesEverywhere`): a link signs in as its member in all of their projects, so minting one for someone who already has their own way in, or who is also in a project the owner has no say in, would let the owner act as them. A fresh link ends any link the member still had pending. The token travels in the URL fragment, so it never reaches a server log; only its hash is stored, it works once, and it becomes an `HttpOnly`, `SameSite=Lax` session cookie. A member can also **connect GitHub** (the GitHub App's user authorization, callback `/auth/github/callback`); the account is then an identity for **Sign in with GitHub**, and its tokens are stored encrypted with a key only the server holds. Connecting starts from the board (`POST /auth/github/link`, like every write); an account connected to another member stays theirs until they disconnect it, and connecting a different account drops the sign-in the previous one gave. A sign-in link opened in a browser signed in as a different member asks before it replaces that session. GitHub alone never creates a member. When the member whose approval passes a verification has GitHub connected, the engine, after marking the spec `Implemented`, approves the pull request **as them** at its current head, so the review counts as theirs; it is tried once and recorded as `github_approved` or `github_approval_failed`. Before approving it reads the pull request's reviews: when the member's approval of that head is already there (a record lost to a crash or a failed write right after GitHub took it), it is recorded and not sent again. When the project allows auto-merge (`pull_request.auto_merge`) and the chooser chose `merge: auto` for this result, it then turns on auto-merge as them, pinned to that head (or merges straight away when GitHub reports it already mergeable), recorded in the `github_approved` event's `merge`. Otherwise it stops there: once its part is done the engine records `awaiting_merge` and the board shows the pull request as approved and waiting for a person to merge it on GitHub, or `merge_held` when the branch holds commits nobody verified (it moved past the verified head, or a push raced Officina's own status commit), and the board says not to merge until they are reviewed. A build round that pushed opens the task's pull request; when GitHub fails at that moment, or the process dies right after the round is applied, the scheduler opens it on a later pass from the result the round recorded before it was applied (`openMissingPullRequests`), and opening it again returns the one already open. A developer's hand-in has no run, so it records its title and checks as a task event in the same transaction as its push (`build_handed_in`), and the catch-up opens the pull request from whichever build came last, an agent's round or a hand-in. When the project sets `pull_request.copilot_review: true`, the scheduler also asks Copilot to review each pull request Officina opened, on its first pass after the pull request is linked to the task (Officina's pull requests are never drafts; checking on every pass, not inside the build step, means a crash right after opening loses nothing, and turning the setting on covers tasks already in flight), **as the member who requested the task**: the App has no Copilot seat, so a branch rule that asks for Copilot's review does not start it on the App's pull requests, while a request from a person with a seat does and is billed to that seat. It calls `POST /repos/{owner}/{repo}/pulls/{number}/copilot-code-review` with the member's token, once per pull request, recorded as `github_copilot_review_requested` (a review already pending counts, and so does one Copilot already left, which is read first, so an attempt whose record was lost is not asked again) or `github_copilot_review_failed` with the reason (no connected account, an authorization that cannot be refreshed, or GitHub refusing because the member has no seat or quota); a failure never blocks the task. Without a connected account people approve and merge on GitHub as before. Emailed magic links and Google sign-in come next, for everyone; linking a GitHub account is optional: it only lets Officina submit the verifier's approval on GitHub for them, and merging is always done on GitHub, linked or not. Actions Officina performs on GitHub are done by the Officina GitHub App and name the member who triggered them. A merge approval is submitted with the member's own GitHub user token, so it counts as their code-owner review.

## 3. Collaboration model

- **Workspace -> projects -> tasks.** A workspace is a team (for example one company). A project is one repository plus its config. A task is one request, from first idea to merged change.
- **Requests.** Anyone with contributor rights starts a request in plain language. The interviewer agent asks follow-up questions in the task thread until the request is specific enough to spec. Other members can join the thread, add context or screenshots, and vote. Mechanics: a new request stays in `request` and the interviewer runs; a question becomes an interviewer comment plus a block asked of the requester, whose answer runs it again; at most four questions, then it must finish; finishing posts a summary with "done when" checks, renames the task in the requester's words and submits it to triage. The requester or a maintainer can submit as is at any time, which closes an open question.
- **Questions with options and previews.** An interviewer question, or a spec agent's `blocked` question, may offer two to six options (`options` in the contract, `packages/core/src/questions.ts`), each with an optional preview of what people would see: the wording `before` and `after`, a Markdown example, a small static HTML mock, or an https link to a screenshot or preview build. The agents are told to add a preview whenever the answer changes something people will see, so a person who does not read code chooses by looking. The options live on the task's `blocked` value and go by letter, (a) to (f); the thread lists them, the board shows each with its preview and a Choose button, and the connector's `show_task` returns them for Claude to show in chat. Picking one answers with its letter and label (`optionAnswer`) plus any note, only while the same question is still open: the board and the connector send back the task version the question was read at, and a pick from any other version is refused with a request to look again; writing an answer in words always works. Previews are agent-written: Markdown goes through the sanitized renderer, an HTML mock is sanitized and drawn in a sandboxed frame with its own policy that loads nothing remote, and a link only opens in a new tab. `intake.interview: false` in the project config, or skipping it per request, goes straight to triage.
- **Triage.** Maintainers see new requests in a triage column: merge duplicates, set priority, move to speccing, or decline with a reason. Votes inform priority, they never decide it.
- **Threads.** Every task has one thread: comments, @mentions, attachments, agent messages and system events in one timeline. Agents read the thread as data, never as instructions.
- **Spec review.** Specs are versioned documents with inline comments and suggested edits. The spec agent revises the spec from the comments; approvals always refer to a specific spec version.
- **Approval policies.** Each lane defines who must approve each human gate, as roles or approval domains with a quorum (for example "requester AND one `product` approver"). Policies are config, not code. Two rules hold whatever a policy says: a requirement that no current member can meet (for example a `product` approver when nobody holds that domain) is **waived and recorded as waived**, so a one-person project is never stuck and a new member's requirements switch on the moment they join; and every gate always needs **at least one maintainer or owner**, a floor that is never waived. One member's approval satisfies every requirement they are eligible for, unless the project turns off self-approval for requesters (section 2). Only members whose role may take the gate's action (`approve_spec`, `verify_result`) count at all.
- **Assignment.** Build and review steps have an assignee: an agent role, or a member who claims it. A member can take over from an agent mid-task (the branch and the thread carry the context) and hand back. Taking a build over ends the agent's part: nothing its run ends with (a result, a block, a failure) applies to the task once the assignee changed or the run was stopped, even after the member lets go and the agent is given the build again, and on its next pass the scheduler fails that run and interrupts its session (`failTakenOverRuns`), whatever stage the member's work reached meanwhile, as it does for runs a previous process left. A run stopped before its session existed is interrupted by its own step as soon as the session is recorded, before the brief is sent. Only refs moved outside the task branch during the run still block the task, for a maintainer to check.
- **Claude connector.** A member can add Officina to Claude once (claude.ai Customize > Connectors > Add > Add custom connector, which also reaches the desktop app; or `claude mcp add` in Claude Code) and then open requests, see what waits on them, list every task in progress, read a task with who asked and who approves each gate, hand in a build they claimed, answer questions, comment and approve or ask for changes from chat. The connector is a remote MCP server at `/mcp` (Streamable HTTP, stateless JSON, protocol revisions 2025-03-26 to 2025-11-25, the ones Claude's connectors speak). Officina is its own OAuth 2.1 authorization server for it: protected resource metadata (RFC 9728) at `/.well-known/oauth-protected-resource/mcp`, authorization server metadata (RFC 8414), dynamic client registration for public clients, the code flow with PKCE S256 only, tokens bound to the `/mcp` resource (RFC 8707), one-hour access tokens and 30-day refresh tokens that rotate, where replaying a spent one revokes the whole grant. Rotation holds the refresh token's row in one transaction, so two concurrent uses can never both rotate it and a replay revokes even the tokens issued a moment before; a spent refresh token is kept until its own expiry so a late replay is still caught. Task links from the connector name the project (`/tasks/12?project=<id>`), since numbers are per project, and the board switches to it. Consent happens on the board's `/connect` page, signed in as usual (a link or GitHub), so a connector always acts as an existing member and never creates one. Every problem with an authorization request is shown there as a code the board words with fixed text, never sent to the client's redirect: the browser goes to the redirect only after the person allows or refuses. The consent page leads with the host the app returns to and says that the app's name is its own, unverified. Without a request, `/connect` lists the member's **connected apps** (one per grant, with the hosts it returns to and when it last renewed its token), and revoking one deletes every token of that grant at once; a member's grants and pending codes also end when their last project role is removed (a trigger on `project_roles`), so being added again later does not bring them back. `show_task` fences everything people and agents wrote (the request, the plan, the question and its previews, the comments) with `fence` from the engine and says it is data, and `review` is marked destructive. Each tool calls the same code as the board's API (`createRequestAs`, `actOnTaskAs`, `boardView`, `taskView`), so roles and policies apply unchanged. Tool descriptions are written for Claude guiding someone who is not a developer: what to ask before opening a request, three example requests, and never to approve without the person confirming the checklist. Client ID metadata documents are not offered yet: Claude falls back to registration, and fetching arbitrary client URLs from the server would need its own hardening.
- **Notifications.** In-app inbox for everything that needs a person: approvals, questions, mentions. Delivery by email and web push; chat integrations later. Each member picks their channels.
- **Presence.** The board and task pages are real-time for everyone viewing them: who is looking, who is typing, which agent is running.
- **GitHub mirror.** Each task has a linked issue; stage changes and decisions are mirrored there as short comments, so the trail is visible to people who never open Officina. Commands in issue comments (`/approve`, `/changes`) are accepted from linked members and follow the same policies.

## 4. System overview

```
  Board (SvelteKit PWA) <--- Server-sent events -----+
        |  HTTPS                                      |
        v                                             |
  API (Bun + Elysia) ---- Engine (deterministic) ---- Postgres (state, events, audit)
        ^                    |          |
        |                    |          +--> Notifier (email, push)
  GitHub App webhooks        |
        |                    v
  GitHub (repo, PRs, CI) <-- Runner interface
        ^                    |
        |                    +--> Managed Agents (primary): versioned role agents,
        |                    |    sandboxed sessions, event stream, budgets
        +--- git proxy ------+--> GitHub Actions + Agent SDK (fallback)
                             +--> self-hosted worker (later)
```

| Component      | Responsibility                                                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **Board**      | Every human surface (section 9). Installable PWA so approvals work from a phone.                                                         |
| **API**        | Auth, members, tasks, threads, approvals, config; webhook intake from GitHub and from the runner.                                        |
| **Engine**     | State machine, scheduler (priorities, WIP limits), dispatcher (starts runs), claim and lease handling, healer sweeps, policy evaluation. |
| **Postgres**   | Single source of orchestration state; append-only `task_events` is the audit log. `LISTEN/NOTIFY` feeds the realtime channel.            |
| **Runner**     | Executes one agent role for one task step and streams events back. Pluggable (section 7).                                                |
| **GitHub App** | Installed per repository: reads code, pushes `officina/*` branches, opens PRs, mirrors comments, receives webhooks.                      |

**Realtime.** Triggers on tasks, task events, comments, runs, run events and learnings call `pg_notify`, so every writer (engine, CLI, webhooks, API) reaches open boards without knowing about them. The API holds one `LISTEN` connection and fans changes out over server-sent events, filtered to the projects each viewer belongs to. Events only say what changed; the board refetches, so a missed event costs a refresh, never a wrong state. Server-sent events rather than WebSocket: the board only listens, and every action is an ordinary authenticated `POST`.

Stack: Bun, Elysia, Postgres (raw `pg`), SvelteKit with Svelte 5 for the board, deployed on Fly.io. One boring stack; deviations need a reason.

## 5. Task lifecycle

Stages are columns on the board. Flags (`blocked`, `paused`) overlay any stage.

| Stage         | Worker                               | Enters when               | Leaves when                                                                                    |
| ------------- | ------------------------------------ | ------------------------- | ---------------------------------------------------------------------------------------------- |
| `request`     | contributor + interviewer agent      | a member starts a request | the interviewer marks it specific enough, or a maintainer moves it on                          |
| `triage`      | maintainers                          | request is complete       | prioritized -> `speccing`; merged as duplicate; declined with a reason                         |
| `speccing`    | spec agent                           | triaged                   | spec version posted -> `spec_review`; missing fact or decision -> `blocked` with a question    |
| `spec_review` | chooser agent, then people           | spec version posted       | chooser plans the approvals, then policy satisfied -> `ready`; changes -> `speccing`           |
| `ready`       | engine                               | spec approved             | WIP slot free and assignee set -> `building`                                                   |
| `building`    | builder agent or a member            | dispatched or claimed     | branch pushed and checks pass -> `reviewing`; red lane requires a member                       |
| `reviewing`   | reviewer agents (+ optional members) | branch ready              | all reviewers approve -> `choosing`; changes -> `building` fix round (bounded)                 |
| `choosing`    | engine + chooser agent               | reviews approved          | approvals planned, verifiers and checklist assigned -> `verifying`; auto-verified -> `merging` |
| `verifying`   | people, per lane policy              | checklist posted          | policy satisfied -> `merging`; change requests -> `building`                                   |
| `merging`     | code owner                           | verified                  | PR merged -> `done`; CI red -> `building`                                                      |
| `done`        | learner agent (async)                | merged                    | learnings recorded; never blocks the task                                                      |

- **`blocked`** always names a person or a role and a precise question. The first answer in the thread clears it and resumes the stage that blocked.
- **Handed to a person.** When a task needs something agents can neither do nor decide, an agent (the interviewer, the spec writer, the builder or the onboarder) returns `needs_person` instead of guessing or stalling: which of the needs in `HANDOFF_NEEDS` (`packages/core/src/handoffs.ts`) apply (new infrastructure, something the tools cannot do, a secret, a domain or DNS change, a new host, a third-party account, access or who can see something, publishing somewhere new, a decision only the owner can take), why, and each thing the person must provide. The engine, not the agent, decides who it goes to: the owner when any need is the owner's, otherwise a maintainer. The task is held like a question, with the needs recorded on it (`blocked.handoff`), and the board, the inbox and the connector show it as "Agents cannot go on: needs the owner for ..." with the list. Answering it resumes the stage.
- **Needs a developer.** A task waits in `ready` for a person, not the build agent, when its lane forbids agents or when the chooser's plan for the spec asked for a person (`approval.build: person` with a reason, for work too big or too risky for agents, such as a large port of a design into the app). Like every plan field it only gets stricter: a later plan cannot hand the build back. The engine never dispatches such a task (`humanBuildReason` in `packages/core`), and the board shows "Needs a developer" with the reason to every member with `build`: maintainers and owners, and any contributor with the `developer` domain, so a project can bring in a developer without giving them triage, merge or steering. One of them claims the build (the board, the CLI `task claim`), builds it on `officina/task-<number>` by hand or with their own agents (Claude Code with the connector, for example), pushes, and **hands it in** (the board's "Hand in the build", `POST .../hand-in`, the connector's `hand_in_build` or the CLI's `task hand-in`). `handInBuild` (`packages/engine/src/hand-in.ts`) reads the push from GitHub, never from the person, applies it as theirs through the same `push` command an agent's build uses (lanes, guardrails, the catalog check, the two reviewer agents next) and opens the pull request; repeating it only opens a pull request a failed first call left. A hand-in carries a pull request title and what was checked and left unchecked, held to the builder's own contract: `INPUT_LIMITS` and `checksSchema` (`packages/core/src/limits.ts`) set every field's length and the 30 checks of each kind once, for the board's API, the connector and the agent contracts alike, so the same words are accepted whichever way they arrive. Taking a build over from the agent needs `build`; taking it from another person needs `steer`.
- **Claims and leases.** A worker (agent run or member) holds a lease on a step. Leases expire; the healer releases stale ones and re-dispatches or notifies.
- **Reviews on GitHub count.** A review left on the pull request for the current head (Copilot's inline comments, or a person asking for changes) sends the task back to building with those comments as notes, from `reviewing` up to `merging`. A person counts only when GitHub reports them as an owner, member or collaborator of the repository, so a stranger on a public repository cannot write the builder's next brief; a review of an earlier head is ignored, except of Officina's own commit that only sets the spec's status line, which counts as the task's head. A Copilot review (from an account in `COPILOT_REVIEWERS`) with nothing on the code counts too when it gives a verdict (green "Approval recommended", blue "Needs a closer look", yellow "Changes recommended", read from the body by `copilotVerdict`, since Copilot always submits a comment-state review): the builder checks each point of its overview like an inline comment. Any other bot counts with inline comments; with none it counts only when the project lists it in `pull_request.review_bots` (the review bots the repository runs, such as CodeRabbit or a Claude review action), and then a review body or a comment it posts on the pull request's conversation counts as an overview. A comment is recorded with every edit (`github_comment_seen`) and reaches the builder only once it has not changed for `COMMENT_SETTLE_SECONDS` (`forwardSettledComments`, on every scheduler pass), as it last read, since review actions post a placeholder and edit it as they work; the settled comments of one round go to the builder together. A comment is tied to no commit, so it is taken to be about the head the task holds, and one from before the builder's last push or answer is dropped; people's plain comments never count, since one may only be a question. Such an overview-only review or comment is not sent back when the task's last request for changes was an overview-only one by the same bot, so a bot reviewing every push cannot loop the task. A round answering a GitHub review may finish `unchanged` (no push: the head stays and the task goes back to `reviewing`), and its `reviewReply`, what the builder checked and changed or why not, is posted on the pull request; the engine requires it when the review asked for a closer look. Whenever work leaves `merging` (a review, or failing checks) the webhook turns auto-merge off, whether Officina or a person turned it on, and the scheduler retries every pass for any task whose trail still records it as on, until GitHub confirms it (`github_auto_merge_cancelled`); the engine re-reads the task before it approves. Once the fix is reviewed again and verified, the engine resolves the threads of the reviews it forwarded, since branch rules usually require resolved threads.
- **Checks on GitHub count.** A failed check suite or commit status (`status`, what CI outside GitHub Actions and deploy previews report with) on the task's head, or on Officina's own status commit on it, sends the work back to building with what failed, from `reviewing` up to `merging`, so nobody reviews, plans, verifies or merges a head whose checks are red. Both are found by commit, not by pull request, since a suite started by a push lists no pull request and a status never does. A failure on an earlier head is ignored, and one while the task is building is left to the round in progress.
- **Pushes from outside count.** The task branch can move without Officina: a review bot pushes its fix, a person commits on it, someone updates it from the default branch. On every scheduler pass, before the merge work, the engine reads the pull request's head for each task from `reviewing` up to `merging`. A head that carries exactly the change people verified, every file of the change with the same content against the default branch (`changeOf`, `changeFingerprint`), is an update from the default branch that touched none of it: it is recorded as `head_carried` and stands for the task's head from then on, so the reviews, the plan and the verification stand, the merge handoff (approval as the verifier, auto-merge, or a person's merge) runs again for it, and checks red on it still send the work back. At `merging` the carry waits until GitHub confirms auto-merge off, since it was pinned to the old commit; whether auto-merge is on still counts from `merging`, so an attempt from before the carry is never hidden. The carry is written under the task's row lock, only while the task is at the stage, head and expected head it was compared at (`recordHeadCarried`), so a push that lands meanwhile wins. Any other head that is neither the task's head nor a commit standing for it is taken in like a build round's push (`outside_push`, recorded as `pushed` with `outside: true`): the lane is recomputed from the real diff, the guardrails run, and the task goes back to `reviewing`, so the reviewers, the chooser and the verifiers look at the new head and approvals of the old one no longer count. It is not a fix round. A task taken out of `merging` this way gets auto-merge turned off, since a person may have turned it on and GitHub would land the new head once its checks pass. Checks that already failed on the new head are read from GitHub (`failuresOn`) and send it back to the builder, since GitHub reported them before any task held that commit. Adoption runs before the pass collects its due steps, so the reviewers and the chooser it starts are those of the new head. While a build run is still going nothing is taken in, since its push and the status commit after it are not recorded yet.
- **Onboarding comes first.** A project registered without the agent docs its config requires (section 11) gets an **onboarding task** (`kind: onboarding`) before anything else: it starts at `spec_review` with a spec the engine writes, listing what is missing, so people approve it like any other, and it is built by the onboarder instead of the builder. While it is open the engine dispatches no other build in the project: `dispatch` fails with `awaiting_onboarding`, and the board says which task the build waits for. The gate holds only dispatches, so the onboarding task itself is never held by it, and a build already in flight when it opens runs to the end; projects registered before the gate shipped are untouched until `add-project` runs for them again. Merging its pull request lifts the gate, and so does cancelling it, which is a person's decision; registering the project again once every required page is on the default branch cancels the open onboarding task itself. An onboarder run that fails holds the task for a maintainer like any other, who answers to retry or cancels. People can still spec requests meanwhile, and a maintainer can still claim one by hand.
- **Fix rounds are bounded** (default 2 per stage). Past the bound the task is blocked for a maintainer, never looped forever.
- **Nothing skips a human gate it was not configured to skip.** Transitions out of `spec_review` and `verifying` are only accepted from members who satisfy the lane's policy; the only way past `verifying` without one is auto-verify (section 8).

## 6. Agent roles

Each role is a versioned agent definition (system prompt, tools, permission policy, model) stored in this repository under `agents/<role>.md` and applied to the runner. Every run records the role version it used. Every role's system prompt is its own prompt followed by the universal code standard, [`standards/code.md`](../standards/code.md), read in one place (`packages/runner/src/standard.ts`), so the spec writer, the builder, the reviewers and the learner hold the code to the same numbered rules, and a change to the standard becomes a new version of every agent on the next sync. Other repositories link that file and never copy it.

Model ids live in one place, `packages/runner/src/models.ts`, by tier. The Opus tier resolves once per process to the newest `claude-opus-*` the Models API lists (by creation date), falls back to a pinned id when the lookup fails or takes more than 10 seconds, and yields to an explicit `ANTHROPIC_MODEL`; the boot log line `model in use` says which model and why. Effort is set explicitly on every agent, because the default moves between releases. Requests stay within what new Opus releases accept: thinking is never disabled and tool use is never forced (`submit_result` is offered, not required). The engine syncs the role agents on every boot, so a new Opus release or a merged prompt change becomes a new agent version on the next restart; unchanged definitions are left alone. Roles return a JSON contract the engine validates; invalid output fails the run instead of moving the task.

| Role                           | Reads                                                               | Tools                                                       | Returns                                                                                                             |
| ------------------------------ | ------------------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **Interviewer**                | request thread, project product docs                                | read-only repo access                                       | next question, or `complete` with a structured request                                                              |
| **Spec**                       | request, thread, project docs and spec template, code               | read-only repo access                                       | spec markdown, predicted file scope, predicted lane, or `blocked` with a question                                   |
| **Builder**                    | approved spec version, thread, fix notes                            | edit, bash (allowlist), git on `officina/*` branch          | `pushed` with branch and verify results, `failed` with output, or `blocked`                                         |
| **Reviewer: spec conformance** | spec version, diff                                                  | read-only                                                   | `approve` or numbered `changes` with file:line                                                                      |
| **Reviewer: correctness**      | diff, the project's agent docs, the code standard                   | read-only                                                   | `approve` or numbered `changes` with file:line and the rule each one breaks                                         |
| **Chooser**                    | diff, spec, lane result, approval policy                            | read-only                                                   | user-visible or not, verifiers per policy, who builds it (at the spec), verification checklist, before/after tables |
| **Learner**                    | full task history (thread, spec versions, runs, reviews, overrides) | read-only                                                   | 0-3 learnings, each with evidence and a proposed change                                                             |
| **Onboarder**                  | the onboarding spec, the code and git history, the required pages   | edit, bash, git on its `officina/*` branch, agent docs only | `pushed` with branch, verify results and follow-ups (smells found), `failed`, or `blocked`                          |

Builder profiles (`frontend`, `backend`, `infra`, `tests`), prompt and tool overlays on the builder role chosen from the spec's file scope, are planned; today every build task gets the one builder.

The builder and the onboarder are the two **build roles** (`BUILD_ROLES` in `packages/core`): each kind of task has one, the engine dispatches it, and only it may push the task branch. The onboarder writes the docs its prompt describes from the code itself, never by copying the standard; a push that changes anything outside the entry document, `CLAUDE.md` and the agent docs folder trips the `outside_agent_docs` guardrail and blocks the task for a maintainer. The smells it finds come back as follow-ups that the engine puts in the pull request body.

## 7. Runner

The runner interface is small: `start(role, task, step) -> run`, a stream of normalized `run_events`, `cancel(run)`, and a final typed result.

### Managed Agents (primary)

| Officina concept               | Managed Agents object               | Notes                                                                                                |
| ------------------------------ | ----------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Agent role at a version        | Agent (versioned)                   | `agents/<role>.md` applied once per change; runs pin `{id, version}`                                 |
| Project build environment      | Environment                         | `limited` networking with package managers allowed; extra hosts listed per project                   |
| One step of one task           | Session                             | `github_repository` resource checked out at the task branch; `initial_events` carries the step input |
| Live log on the board          | Session event stream                | normalized into `run_events`; webhooks for state changes                                             |
| Cost per step and per task     | `usage.list_cost`, session `budget` | budget per step comes from the lane config; a paused-at-budget session asks a maintainer             |
| Which tool calls need a person | `always_allow` permission policy    | none waits on a person; web tools are off, and write tools are off for read-only roles               |

- **Secrets never enter the sandbox.** Git access goes through the Anthropic-side git proxy, which injects the repository token after the request leaves the container. Other credentials use vault `environment_variable` entries limited to specific hosts.
- **Results come through one tool.** Every role ends by calling a custom `submit_result` tool whose input schema is generated from the role's output contract. The engine validates the call; an invalid result goes back to the agent with the problems listed, and a third invalid result fails the run.
- **Repository access is scoped by token, not by prompt.** Roles that only read receive an installation token with read-only contents permission, so even a manipulated agent cannot push. Only the build roles (builder, onboarder; `BUILD_ROLES` in `packages/core`) get write access, and only their task branch `officina/task-<number>` is accepted: a push anywhere else fails the step and blocks the task.
- **Stale results are discarded.** A result is applied only if the task is still in the state the agent worked on (same stage, spec version and head commit, not blocked or paused), checked on the locked row. Parallel reviewers therefore do not conflict, while a result for work that people changed meanwhile is dropped.
- **One active run per task and role**, enforced by a unique index, so overlapping scheduler passes never start the same work twice. Every step, the learner's included, starts the same way: it checks the task is due, the project installed and the role's agent synced, then claims its run (`claimStep`); the step then runs as separate phases (gather its inputs, run the session, guard the refs, apply the result, mirror it to GitHub), so a change to one role's behaviour lands in the phase it concerns.
- **The agent pushes a branch; Officina opens the PR** with its GitHub App after the engine's own checks, so the sandbox never needs PR permissions.
- **Beta.** Managed Agents is in beta, which is why the runner is an interface.

### GitHub Actions + Claude Agent SDK (fallback)

A `workflow_dispatch` workflow in the consumer repository runs the Agent SDK with the role definition. It authenticates to Claude with workload identity federation and to Officina with the job's OIDC token. Trade-off: on public repositories Actions logs are public, so agent output must go to Officina, not the log.

## 8. Lanes, the chooser and approval policies

- A project config lists path globs per lane. The spec agent predicts a lane from the file scope; the engine recomputes it from the real diff after every build round. **The stricter lane wins**, and only an owner can lower it, with a reason recorded in the thread.
- Each lane defines: whether agents may build, WIP limit, diff-size limit, per-step budget, and the approval policy for `spec_review`, `verifying` and merge.
- The **chooser** does the judgement a glob cannot: is the change user-visible, which approval domains apply, which specific members are the best verifiers (requester, area owners, recent editors), how deep the check should be, and what exactly to look at. For text-only changes it produces before/after tables so verifiers never read a diff.
- **Approval plans.** The chooser runs at both human gates: on each spec version before anyone may approve it (approving an unplanned version fails with `not_planned`), and on each pushed head before verification. Its plan holds a check depth (`glance`, `test`, `device`), a rationale people read, named verifiers (a request, not a requirement), extra requirements (domain approvals or the owner role) and, for the spec, who builds it (`build`: `agent`, the default, or `person` with a reason), and for the result, who merges it (`merge`: `person`, the default, or `auto`). The effective policy for a gate is the lane policy plus those extras. Plans only ever add: extras accumulate across every plan for the same gate, once a plan for the result asks for a person to merge no later plan can hand the merge to GitHub, verifiers must be contributors, and only a maintainer may mark a change as not user-visible. A domain nobody holds is waived like any other requirement, so a plan can raise the bar but never deadlock a small team. Each plan is recorded as an `approval_planned` event with what it added.
- **Auto-verify.** A green lane with `auto_verify: true` lets a result go from `choosing` straight to `merging`, recorded as `auto_verified`, only when the project's `release.on_merge` is not `production` and the chooser's plan for the result adds no requirement and asks for no more than a glance. Anything that touches a stricter path is not green, a merge that deploys to production always gets a person's check, and the chooser keeps the human gate by raising the depth or adding an approval. The spec is still approved by people. Who merges follows the next point.
- **Auto-merge.** Off unless the project sets `pull_request.auto_merge: true`, and even then it is the chooser's call for each result: it picks `merge: auto` only for low-risk changes with nothing to coordinate and an easy way back. With both, the engine turns on GitHub's auto-merge (as the verifier, after their own approval succeeded, or as the App for an auto-verified result), so the branch rules still decide when it lands; it is tried once per time the task reaches `merging`, recorded as `github_auto_merge` or `github_auto_merge_failed`, separately from the approval. A failed attempt may still have reached GitHub, so the scheduler turns auto-merge off and waits for GitHub to confirm (`github_auto_merge_cancelled`) before recording `awaiting_merge`, so a person is never asked to merge while GitHub might. Without either, the engine records `awaiting_merge` and a person merges on GitHub. GitHub's expected-head check only applies when auto-merge is turned on, so on every scheduler pass while the task waits in `merging` the engine reads the pull request's head: anything other than the verified head (or Officina's own status commit on it) is normally taken in as a push from outside (section 5) earlier in the same pass; when it is not (the read failed, or a push landed between the two reads), the engine records `merge_held` once per such head, and the scheduler turns auto-merge off until GitHub confirms. The board shows the choice in the plan and whether auto-merge is on.
- **Calibration.** Every chooser verdict is compared with what people did: verified with no changes suggests over-gating, sent back suggests under-gating. The learner uses these outcomes.

## 10. Auto-learn

1. **Once per merged task** (within 14 days of `done`) the scheduler runs the learner on a read-only token. Its brief is the whole history as data: request, final spec, every event with actor and time (review notes, change requests, questions and answers, guardrails, approval plans), agent runs with cost and duration, the thread, and the learnings already proposed or rejected so it does not repeat them. A failed attempt is recorded and never retried: learning is optional.
2. It proposes **at most three learnings, often none**. Each has a lesson, its evidence, and an **exact edit** to one of three targets (`LEARNING_TARGETS` in `packages/core`): `docs`, the project's agent docs (its entry document and the pages of `docs.standards`, a new page there included, never a tool layer such as `CLAUDE.md`, which only points at the entry), the first place for a lesson about structure, patterns, shared code, testing or pull request rules, since every later agent reads them; `project`, any other Markdown file in the project (never a protected path); or `agent`, an Officina role prompt (`agents/<role>.md`). The edit adds text after an excerpt found exactly once, or appends it. The engine checks every edit applies, and that its file matches its target, before accepting the result, so what people see is what would land.
3. Maintainers **accept or reject** each learning on the board. Accepting a `docs` or `project` learning re-applies the edit to the current default branch, pushes `officina/learning-<id>` and opens a pull request titled `docs(ai): ...` or `docs(learning): ...`; people merge it as usual, and the merge marks the learning applied. The decision is recorded last, so an accept that fails halfway leaves the learning proposed and can be accepted again: the branch it left is kept, the edit is written only if the branch lacks it, and the pull request already open is reused. Rejecting a learning closes any pull request such an accept left open, from the edit's branch and from the first one, so nobody merges an edit people turned down. A learning can wait while its file changes on the default branch; when its edit no longer applies, accepting it hands it back to the learner instead, which rewrites the edit against the file as it is now (or says it could not, when the file already says it, the run fails, the project cannot run the learner at all, or the engine lost the rewrite's run twice, since a lost run is retried only once), and the learning stays proposed so people decide the new edit. A decision names the edit the person read (when it was last rewritten), and accepting an edit rewritten since is refused, so a board open from before the rewrite never accepts text nobody saw. Officina never writes to its own repository, so accepted agent learnings stay listed for Officina's maintainers to apply; a merged prompt change becomes a new agent version on the next deploy (or `setup-agents`).
4. Later: a weekly synthesis groups learnings across tasks, so one-off noise does not become policy.

## 11. Project config

Lives in the consumer repository at `.github/officina.yml`. Members and roles are managed in Officina, not in this file.

```yaml
version: 1
docs:
  entry: AGENTS.md # what every agent reads first
  spec_template: docs/specs/template.md
  spec_dir: docs/specs # the engine sets a spec's `Status:` line to In progress / Implemented
  standards: docs/ai # the agent docs folder (the default); its pages default to DEFAULT_STANDARDS_PAGES
  pages: [README.md, structure.md, reusability.md] # only when a project needs other pages, relative to the folder
  catalogs: # a file added under the glob must be listed on the page, relative to the docs folder
    'src/lib/components/**': reusability.md
pull_request:
  title_pattern: '^(feat|fix|docs|chore)\([a-z-]+\): .+$' # the builder's PR title must match
  auto_merge: false # true lets the chooser decide, per result, that GitHub merges it once checks pass (section 8)
  copilot_review: false # true asks Copilot to review each pull request Officina opens, as the task's requester (section 3)
  review_bots: ['coderabbitai[bot]'] # bots whose comments and review overviews reach the builder (section 5)
guards: # the security wall (section 13); every list is optional
  confidential: ['room/**'] # files whose content is confidential
  confidential_terms: ['investor', 'cap table'] # words that mark a request as about it
  publishing: ['CNAME', 'firebase.json'] # files that publish, deploy or open access
approvals:
  self_approval: true # false: the requester's own approval meets only `requester: true`; roles, domains and the maintainer floor need someone else (section 2)
verify: ['npm ci', 'npm run lint', 'npm run check'] # run by the builder before pushing
release:
  on_merge: staging # what merging into the default branch deploys: production (the default), staging or nothing
board:
  look: tecnica # the board's look until a member picks their own: modernista (the default) or tecnica
lanes:
  red:
    paths: ['.github/**', 'src/payments/**']
    agents_build: false
    approvals:
      spec_review: [{ role: owner }]
  standard:
    paths: ['**'] # everything not matched by a stricter lane
    wip: 3
    diff_lines: 800
    budget_usd: 25
    approvals:
      spec_review: [{ role: maintainer }]
      verifying: [{ domain: product, when: user_visible }, { role: maintainer }]
  green:
    paths: ['src/i18n/**']
    auto_verify: true # green only: results skip a person's check when nothing calls for one (section 8)
    wip: 5
    budget_usd: 5
    approvals:
      spec_review: [{ requester: true }, { domain: product }]
      verifying: [{ requester: true }]
```

**Agent docs.** Every project follows the universal code standard ([`standards/code.md`](https://github.com/AntonioVentilii/officina/blob/main/standards/code.md)) and holds its own agent docs: the `docs.entry` document plus the pages of `docs.standards`, read off the code (structure, patterns, the catalog of shared code, testing, pull request conventions). `requiredDocs` in `packages/core/src/config.ts` is the one list of what a project must hold: the entry, every page and every catalog page. The correctness reviewer holds each change to the project's pages and the standard and cites the rule each item breaks (`rule` in its contract), and every catalog is checked mechanically after each build round (section 13). Registering a project (`add-project`) checks each of them on the default branch through the GitHub App; when any is missing it opens the onboarding task (section 5) that writes them, at most one open at a time.

## 13. Security model

- **Agents act only on dispatch from the engine**, never directly on issue text or comments from the outside world. Public issue text is data: it reaches prompts inside a quoted block labelled as untrusted.
- **Least privilege per role.** Read-only roles have no write tools. The engine accepts only the task's own `officina/*` branch as a builder's result. The installation token it hands the builder can still write any ref the App can reach, so it is minted for that run alone and revoked as soon as the session ends, and the engine snapshots every branch and every tag before the run and after the revocation. Two moves are expected and pass: the default branch moving by a pull request merged on top of the old head, and the branch of another task whose own build ran alongside. Any other branch created, moved or deleted during the run is checked against the repository's activity on GitHub (`GET /repos/{owner}/{repo}/activity` for that ref since the run began), which names the account behind each change: it stops the build only when it was changed with Officina's identity, the App's bot login, which is what the builder's token pushes as, or when GitHub names nobody for the change. Pushes by people, release-please, dependabot or any other bot never stop it, and neither does Officina's own work during the run: a spec status commit it wrote and recorded (`spec_status_set`) on that task's branch, or the edit of a learning people accepted meanwhile, pushed to that learning's branch (`branchForLearning`), as long as the branch ends on exactly the commit Officina recorded writing there, on a commit of the default branch; a learning branch holding anything else is checked like any other branch. GitHub's activity does not record who moves tags, and deploys run on `v*` tags, so tags follow what they point at instead: a new tag on a commit already on the default branch (a release) passes, checked with GitHub's compare; a new tag on any other commit, or an existing tag moved or deleted, stops the build, so an agent cannot ship unmerged code. A change that stops the build fails the run, discards its result and blocks the task with a question for a maintainer. The check runs however the session ends, a thrown error included, and counts a comparison GitHub cannot answer as a change; the snapshot before the run is kept on the run (`recordRunRefs`), so a build a restart left unfinished is checked when the engine starts again, after its session is interrupted (`guardOrphanedBuilds`). That check finds a push after the fact; it does not prevent one, so a project must still protect its default branch and tags with a ruleset the App cannot bypass. No role can merge, change branch rules, touch CI secrets or deploy; the token never carries the `workflows` permission.
- **Approvals and merges are pinned to what was verified.** Approving on GitHub as the verifier, and turning on auto-merge or merging, name the expected head: the task's verified head, or Officina's own spec status commit on top of it. A status commit counts only when its parent is that head; on a branch that moved, none is written. When the answer to a status write is lost (the process dies, or the connection drops after the write landed), the next pass finds the branch on that commit and takes it as Officina's own when its only parent is the expected head and it changes only the spec file, to that head's text with the new status line. One exception, decided by the owner: a head carried from an update with the same change (section 5) is approved and merged as the verified head, since every file people checked is the same, byte for byte, and what came in from the default branch is held to the required checks, which run again on it. An update that changes any file of the change is reviewed and verified again. A pull request whose head is anything else is not approved; the mismatch is recorded on the task, and GitHub refuses a merge of any other commit.
- **The security wall.** What no agent may handle alone is decided by rule, in code, and the prompts only repeat it. A task carries **guards** (`GUARDS` in `packages/core/src/guards.ts`), set from the request's words (secrets, access, publishing, and the project's `guards.confidential_terms`), from every later answer and comment by the same rule (`guard_words`), from a handoff that needs a secret, access or publishing, and from the paths the spec predicts and each push changes (`guards.confidential`, `guards.publishing`); they only grow, recorded as `guards_changed`. A guarded request from anyone who may not `publish` is held for the owner before any agent reads it, and submitting it as is cannot skip the hold; an answer or comment from such a member whose words add a guard holds the task for the owner the same way, in place of any question it waited on unless that one is already the owner's. A task guarded for secrets, access or publishing needs the owner's approval at both gates, whatever the lane says, and nothing guarded skips people's check or merges on its own. A confidential task keeps its title, stage and people for every member, but its request, thread, spec, plan, checklist and question are shown only to members with `see_confidential` (and each person's own words to them), through the board and the connector alike, and only they can approve it, send it back, comment on it, answer its questions or claim its build. The reason the chooser gives for a person to build it is part of what they alone read. Every agent result is redacted of anything shaped like a secret (keys, tokens, private keys, `NAME=value` for secret names, passwords in URLs) when it is parsed, before anything stores, shows or posts it, and every connector answer is redacted again; a push that adds or changes a file that holds secrets (`.env`, keys, credentials) never reaches review and is handed to the owner (`secret_files`). Every brief ends with the same rules and the project's confidential paths.
- **Previews are rendered, never trusted.** An HTML mock in a question is sanitized with DOMPurify (no scripts, handlers, forms, frames or remote URLs) and drawn in an `<iframe sandbox="">` whose own Content-Security-Policy allows only inline styles and `data:` images, so it runs nothing, reaches neither the board nor the network, and its styles stay inside the frame. Links must be https and open outside the board. The API shows a question's options only to those who may read the question.
- **People act within their role.** Every check reads the permission matrix (section 2). Watchers read; they cannot open requests (each one starts paid agent runs), comment, or answer questions. An answer's comment is written in the same transaction as the decision, so a refused answer leaves nothing behind.
- **Webhooks apply once.** A delivery id is claimed atomically before processing, given back if processing fails and marked handled when it succeeds, so concurrent redeliveries are never applied twice and a failed one is retried. Deliveries older than a week are purged, since GitHub redelivers only within three days. A claim left unhandled for ten minutes belonged to a process that died while handling it, and a redelivery takes it again under a new claim id, which the old handler can no longer mark or give back. Such a redelivery may repeat effects the dead handler already applied; that is safe, because every webhook effect goes through the lifecycle's stage and head guards and a repeat is rejected (`wrong_stage`, `stale_head`). GitHub does not deliver a missed event again on its own (a deploy restart, a handler error), so on every pass the scheduler reads the pull request of each task in `merging` and, when it was merged or closed, applies the webhook's own handling (`catchUpPullRequests`). It runs right after the pass that may merge a pull request straight away, so a merge Officina made reaches its task in the same pass, and that pass leaves a pull request no longer open alone: nothing is approved on it and nobody is asked to merge it.
- **The connector holds no secrets in the clear.** Codes and tokens are stored as hashes; a code works once, for its client, redirect, PKCE verifier and resource; a token is accepted only for `/mcp`. A redirect is https, or http on the loopback interface for local apps (any port, RFC 8252), and is checked against the registration before Officina ever redirects to it, so a bad request is shown on the board instead of becoming an open redirect. A sign-in started from the consent page returns there only through a same-site path.
- **Credentials do not pile up.** Starting a GitHub sign-in writes nothing: its state carries its own expiry, is bound to the browser by a cookie, and is spent atomically once GitHub accepts the code, before the account is written, so it works once. The scheduler purges expired or spent sign-in links (but each member's latest, whose hash can no longer sign anyone in and shows owners whether the invite was used), sessions and authorization states hourly, along with spent connector codes, expired tokens and connector registrations that never completed an authorization within a day (registering needs no account).
- **Errors stay on the server.** An unexpected error is logged and answered with `{"error":"internal"}`, since its message can quote a GitHub response or a query; a malformed path is a 400.
- **Mechanical guardrails after every build round**, and on every head pushed from outside: files that hold secrets, red-lane paths (when an agent carries the work on), diff size and, for the onboarder, paths outside the agent docs are checked by the engine; a hit blocks the task instead of opening a PR or sending the head to review.
- **The catalog check runs after every build round too**, from the real diff like the lane: a file the branch adds (new, copied or renamed to a new path) under a `docs.catalogs` glob that the catalog page, read as pushed, does not name (by its path or its file name) is a finding (`unlisted_files`, `unlistedFiles` in `packages/core/src/catalogs.ts`); an edit to the page that says nothing about the file does not count. It sends the work straight back to the builder with the finding as a note, keeping the head, as one more bounded fix round, so a shared file nobody listed never reaches the reviewers. It holds for a person building the task as much as for an agent.
- **Credentials stay outside sandboxes** (git proxy and vault on Managed Agents; OIDC on the fallback runner). Officina's own secrets live in the deployment's secret store.
- **Branch protection remains the final authority.** Officina assumes the repository requires human review and passing CI, and never works around it.
- **No tool call waits on a person.** The agents' tools run under `always_allow` (`buildDefinition` in `packages/runner/src/definitions.ts`): which tools a role has, the token it gets and the checks after each run are what limit it. What needs a person comes back as a result instead: `needs_person`, a question, or a guardrail that blocks the task. Unattended safety evaluation is not treated as a human checkpoint.

## 15. Decisions

- **Postgres holds orchestration state; GitHub holds code and the public trail.** Labels and comments cannot carry leases, queues, costs, spec versions or live events.
- **Deterministic engine over an LLM orchestrator.** A looping model session is the least reliable place for scheduling and recovery.
- **Managed Agents as the primary runner** for sandboxing with credentials outside the container, versioned roles, event streaming and hard budgets; behind an interface because it is in beta.
- **Roles in Officina, not repository permissions**, so non-developers can collaborate without write access to code.
- **Merging is opt-in, per project and per result.** A verified result is approved on GitHub as the member who verified it. By default a person merges every result; a project can allow auto-merge, and then the chooser decides for each result, so the riskiest work always waits for a person. When auto-merge is on, the repository's own branch rules, never Officina, are the last word.
