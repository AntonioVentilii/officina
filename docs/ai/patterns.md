# Patterns

The patterns Officina really uses, each with one place to copy from. [`../architecture.md`](../architecture.md) says why; this page says how.

## Domain and state

- **Every change to a task is a command through `decide()`.** A pure function takes the task, a command, the actor and a context, and returns the new task plus the domain events, or a typed error: `decide` in `packages/core/src/lifecycle.ts`. Nothing writes `tasks.stage` any other way.
- **The store applies one command atomically.** `applyCommand` locks the row, decides on current state, writes the task and every event (and the approvals they imply) in one transaction, and runs `onApplied` inside it: `applyCommand` in `packages/db/src/store.ts`. Other multi-statement writes use `inTransaction`, exported from the same file; `addProject` (`apps/api/src/setup.ts`) registers a project with it. Writes that must land with a command take the transaction's client: `insertTask` and `applyCommandIn`, as `createRequestAs` (`apps/api/src/tasks.ts`) opens and submits a request at once.
- **A member acts as `memberActor(memberId, via)`.** A person's action that may come through the Claude connector builds its actor there (`packages/core/src/lifecycle.ts`), passing `via` from `ProjectActor` (`apps/api/src/tasks.ts`) so what the Claude connector does records its app on every event and comment; the views read it back with `viaView` (`apps/api/src/board.ts`), which words it with `CHECK_CHANNEL_LABELS` and `connectionRef`. `decide()` reads `via` for one rule only: an approval through a connected app is refused and proposed instead (`propose_approval`), and the board confirms it.
- **A task's history is written in one place.** Every `task_events` row goes through `appendTaskEvent` and every `spec_versions` row through `saveSpecVersion` (`packages/db/src/task-history.ts`), and a task's number comes from `nextTaskNumber` in `store.ts`; never write those inserts again elsewhere.
- **Agent results only apply to the work the agent saw.** Pass a `guard` to `applyCommand`, as `sameWork` does in `packages/engine/src/step-apply.ts` (stage, spec, head, assignee, and its own run still in progress, `runIsActive`, on a task never paused since it started, `runWasPaused`); the block a failed run asks for takes the same guard, before the run is finished (`failAndBlock` in `step.ts`).
- **A GitHub write is safe to retry: it lands once.** `openPullRequest` returns the pull request an earlier attempt opened from the same branch, and `createBranch` keeps a branch an earlier attempt left, never moving it (`packages/github/src/client.ts`). Accepting a learning writes its file only when the branch does not hold the edit yet (`apps/api/src/learning-pull-request.ts`), so an accept that failed halfway can simply run again, and rejecting the learning closes any pull request it left open (`closePullRequestsFrom`). A decision claims the learning (`claimLearningDecision`, with a lease a stopped process cannot hold past) instead of locking it across those calls, so no transaction waits on GitHub, and renews the claim right before each GitHub write and records under it (`holdLearningDecision` and `decideLearning` in `packages/db/src/learning-decisions.ts`, called from `apps/api/src/learnings.ts`), so a decision whose claim was taken over writes nothing more.
- **What GitHub says about a pull request lands from the webhook, and from a catch-up when the webhook was missed.** Both apply the same writes: a task's pull request through `handleWebhookAction` (`catchUpPullRequests` in `apps/api/src/catch-up.ts` calls it), a learning's through `markLearningsApplied` and `markLearningPullRequestsClosed` (`packages/db/src/learnings.ts`), each a no-op the second time. A learning pull request's state is derived in one place, `PR_STATE` in that file, which the learnings list and the board's task rows (`learningPullRequestsOf`) both read.
- **A comment Officina keeps on GitHub is rewritten from state, and only when its text changes.** The checklist comment is built from what is recorded (`syncChecklistComment` in `packages/engine/src/checklist.ts`), its last text is stored (`checklist_comments`), and the comment is edited only when the new text differs; its first post is claimed with a lease (`claimChecklistComment` in `packages/db/src/checks.ts`), so two writers never post it twice.
- **A person's hand-in meets the checks an agent's build meets.** `handInBuild` (`packages/engine/src/hand-in.ts`) runs the same `titleProblems` and `bodyProblems` the builder's `validate` hook runs (`validatorFor` in `step-session.ts`), and refuses with their words before anything is applied, so a rule of the project holds whichever way a build arrives.
- **An option Officina offers on its own question can carry a decision.** Agents' options are only words, and a picked one reaches `decide` as its answer text. A question Officina asks itself may also mark one of its options with what picking it decides, beside the options in `Blocked` (`allowance`, set by `diffHold` in `packages/core/src/allowance.ts`); the API passes the picked letter on in the `answer` command, and `decide` grants it only to whoever may (`pickedAllowance`, `allowsDiff`). Agent output never sets that field, since no contract has it.
- **Risk comes from the real diff.** Lanes, guardrails and diff size use the paths the GitHub client reads (`pushFacts`), never what an agent says it changed.
- **A step is a sequence of named phases.** `runAgentStep` (`packages/engine/src/step.ts`) claims the run (`claimStep` in `claim.ts`, shared with the learner, whose rewrites claim through `startLearningRewriteRun` under the learning's lock), gathers its inputs, runs the session, guards the refs, applies the result and mirrors it to GitHub, each in its own function over one `Step`: the inputs, brief and session in `step-session.ts`, applying and mirroring the result in `step-apply.ts`. New role-specific behaviour goes in the phase it belongs to, not in a new branch of `runAgentStep`.

## Results and errors

- **Expected failures are values, not exceptions.** Discriminated unions with `ok`: `Decision` (`packages/core/src/lifecycle.ts`), `ConfigResult` (`packages/core/src/config.ts`), `CommandResult`, `RunOutcome`. Error names are a closed union (`DecisionError`, `StoreError`) and the API turns them into words in one table: `ERROR_TEXT` in `apps/api/src/tasks.ts`.
- **Exceptions are for the unexpected**, and a few named classes the caller handles: `SetupError` (`apps/api/src/setup.ts`), `TaskCommandError` (`apps/api/src/tasks.ts`), `GitHubError` (`packages/github/src/http.ts`), and its `RefreshTokenRefused` (`packages/github/src/user.ts`), on which the API forgets the member's spent GitHub account and asks them to reconnect. An unexpected error reaches the client only as `{"error":"internal"}`: the `onError` handler in `apps/api/src/app.ts`.
- **Agent output is untrusted input.** Every role's result is parsed against its zod contract, where every string and list has a ceiling that fits real use and the 65,536 characters a GitHub comment holds, and redacted of anything shaped like a secret (`parseAgentOutput` in `packages/core/src/contracts.ts`, `redactDeep` in `guards.ts`), and project checks run through the `validate` hook of `executeRun` (`packages/runner/src/run.ts`), whose problems go back to the agent. What an agent should know about a field goes in the schema's `.describe()`, which reaches it in the `submit_result` tool, not in a second copy in its prompt (the preview kinds in `packages/core/src/questions.ts`).

## Seams

- **Ports, not clients, inside the engine.** `GitHubPort` (`packages/engine/src/step.ts`) and `ManagedAgentsPort` (`packages/runner/src/port.ts`) are `Pick`s or interfaces over the real clients; tests pass fakes. The real clients are built only in `apps/api`.
- **Text written by people or agents is fenced as data in a brief**, with a fence longer than any backtick run inside it: `fence` in `packages/engine/src/brief.ts`, which every brief uses, and so does the connector's `show_task` (`apps/api/src/connector/tools.ts`).
- **Config is parsed once into a normalized shape.** Code reads `ProjectConfig` from `parseProjectConfig` (`packages/core/src/config.ts`), with defaults filled in, never the raw YAML.

## API and board

- **Realtime is a hint, never state.** Database triggers call `pg_notify` (`officina_notify` in `packages/db/migrations/0005_board.sql`), and a change to a member, which shows in every project they are in, is announced by its own transaction for each of them (`announceMemberChange`), on `CHANGE_CHANNEL` (`packages/db/src/changes.ts`, which the API listens with), the API fans out "this changed" over server-sent events, and the board refetches (`refresh` in `apps/board/src/lib/state/board.svelte.ts`). Which view refetches on which event is decided once, in `apps/board/src/lib/live-events.ts`: a `run` event is a new line of a run's log, sent for every line, so only that run's log reads it (`RunLog.svelte`); the board (`refreshesBoard`) and an open task (`refreshesTask`) refetch on the rest, a change to the run itself included, which comes as a `task` event.
- **Agent-written HTML is drawn only in a sandboxed frame**, sanitized and with a policy of its own (`OptionPreview.svelte`); Markdown only through `Markdown.svelte`.
- **Every board write is a `POST` with the `x-officina-request` header** (`REQUEST_HEADER`, checked by `mutation` in `apps/api/src/api.ts`), so a cross-site form cannot make one.
- **A person's rights are one matrix.** Every check of what a member may do asks `can(member, action)` (`packages/core/src/permissions.ts`), never `hasRole` against a role written at the call site; `hasRole` is left for routing a question to the role it is asked of. Who may answer or read a question (`canAnswer`, `seesQuestion`) who reads a confidential task (`readsTask`), who builds it (`buildsTask`) and who reads the reviewers' findings on it (`seesReviewFindings`) are decided there too, for the lifecycle, the policies, the board and the CLI alike. A new kind of right is a new action in `ACTIONS` with its least role in `PERMISSIONS`, its words in `ACTION_LABELS` and its row in `docs/architecture.md` section 2, which a test compares with the code. The board reads the viewer's actions from the API (`session.can`), never a role.
- **What a viewer may see is decided in the API**, by the permission matrix, in the view builders of `apps/api/src/board.ts` (`PUBLIC_FIELDS` for event payloads). Every member sees every task of their projects; roles change the detail, not which tasks. The board never hides data the API sent.
- **Loads that can overlap only let the latest land.** A refresh or a page's own fetch takes a check from `latestOnly` (`apps/board/src/lib/latest.ts`) before it asks and drops its answer once the check says a newer load has started, as `refresh` in `board.svelte.ts`, the task drawer's `load` and the access log on the Members page do. A load that live events trigger (the board's `refresh` and the task drawer's `load` on task and member events, never on `run` ones; the run log's `load` on its run's `run` events) goes through `coalesce` (`apps/board/src/lib/coalesce.ts`), which never starts one while the last is still running: those events can come closer together than a load takes (a run's log sends one per line, and one engine step writes several task rows), and a new load started on each would leave every answer outrun and the view empty. A load that only a `members` event or a reconnect triggers, such as the access log on the Members page, fetches directly, since those events are rare.
- **The board imports its own modules through `#lib`, with the file's extension** (`#lib/api.ts`, `#lib/state/session.svelte.ts`, `#lib/components/TaskDrawer.svelte`): a Node subpath import set in `apps/board/package.json`, which SvelteKit 3 asks for in place of `$lib`. Its SvelteKit options (the static adapter, the content security policy) live in the `sveltekit()` plugin of `apps/board/vite.config.ts`; there is no `svelte.config.js`.
- **Board state is one class instance per concern** with Svelte 5 runes, exported as a singleton from `apps/board/src/lib/state` (`board`, `session`, `look`, `live`, `clock`, `toasts`, `guide`).
- **A keyed `{#each}` keys by an id, or else by position**, never by text from data: two members can share a name, two requirements can read alike and an agent can repeat itself, and a repeated key crashes the view (`each_key_duplicate`). When the view sends only text, key by index, as `TaskPeople.svelte`, `ApprovalPlan.svelte` and the before/after rows of `Checklist.svelte` do. Text is a key only where the list itself makes it unique: a constant list in the board's code (`TRACK` in `StageTrack.svelte`) or values deduplicated with a `Set` (the locales of `Checklist.svelte`).
- **Work in progress locks what started it, on every board.** A button that starts work on the server is off while its request runs; buttons that change the same thing share one lock, wherever they are drawn, as every GitHub and sign-out button reads `session.changingAccount`. Work the server holds beyond one request (a learning's decision, a task's hand-in, each under its claim) is reported by the API (`deciding` in `learningsView`, `handingIn` on a task's card), so every board shows it with `Working` (and `WorkingTrace` round a learning's sheet) in place of the buttons. An action a board sent stays shown at work until a reload lands, since only that says whether it went through: a board whose reload failed holds the action until a later one replaces the learning or the task (`LearningDecide.svelte`, `send` in `ActionPanel.svelte`). The words each action reads in are set once in `apps/board/src/lib/working.ts`. It is drawn in ink, never yellow.
- **A component that differs per look branches in one place** (`look.current` in markup, or CSS under `[data-look='tecnica']`), never as a second copy. Fucina's rules for the shared board components live together in `apps/board/src/fucina.css`, each starting at the component's root class (`:root[data-look='fucina'] .task-card`), so those components stay one copy under the line limit; a component that draws only in Fucina keeps its own CSS (`AgentMark.svelte` with `agent-mark.css`, `StageStamp.svelte`). Fucina's hues are written once, in `apps/board/src/lib/hues.ts`, and reach columns and roles through `COLUMNS` and `ROLE_MARKS`.

## Anti-patterns found in the code

Named so nobody copies them; each is a follow-up of its own.

- Values the core and the store own are mirrored by hand in `apps/board/src/lib/types.ts`: the stages, lanes and roles, the permission matrix's actions (`ACTIONS` in `packages/core/src/permissions.ts`, mirrored as `Permission`), the gates (`GATES`), check depths (`CHECK_DEPTHS`), build modes (`BUILD_MODES`) and merge modes (`MERGE_MODES`), the learning targets (`LEARNING_TARGETS`) and decisions (`LEARNING_DECISIONS`, mirrored as `LearningDecision` in `apps/board/src/lib/learning-types.ts`), a learning pull request's state (`LearningPullRequestState` in `packages/db/src/learnings.ts`, mirrored in `apps/board/src/lib/learning-types.ts`), the looks (`BOARD_LOOKS`), a sign-in link's states (`LINK_STATES` in `packages/db/src/members.ts`), a run's status (`RunStatus` in `packages/db/src/runs.ts`) and the kinds of an option's preview (`Preview` in `packages/core/src/questions.ts`, mirrored as `OptionPreview`); the terminal stages (`TERMINAL_STAGES` in `packages/core/src/lifecycle.ts`) are mirrored as `TERMINAL` in `apps/board/src/lib/stages.ts`.
- Other values the API owns are mirrored by hand in the board: the request header (`REQUEST_HEADER` in `apps/api/src/api.ts`, written again in `post` in `apps/board/src/lib/api.ts`), the actions a viewer may take on a task (`BoardAction` in `apps/api/src/board.ts`, copied in `apps/board/src/lib/types.ts`), the problem codes (`GitHubSignInProblem`, `AuthorizationProblem` and `ConnectedAppProblem` in `apps/board/src/lib/types.ts`, copies of the ones in `apps/api/src/github-accounts.ts`, `apps/api/src/connector/oauth.ts` and the `unknown_grant` that revoking a connected app answers with in `apps/api/src/api.ts`), and the rule for a path on this site (`localPath` in `apps/api/src/api.ts` and `returnPath` in `apps/board/src/lib/return-path.ts`).
